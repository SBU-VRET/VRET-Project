# MetaHuman (Unreal Engine) Feasibility for Tongue Articulation in a Babylon.js/WebXR/VRM VR Project

## Does the MetaHuman facial rig actually include controllable tongue bones/blendshapes beyond simple protrusion?

### Takeaway
Epic's own DNA rig-definition documentation confirms MetaHuman's skeleton contains four dedicated tongue joints (not just a single "tongue out" blendshape), but the same documentation stops short of describing what articulation (curl, roll, up/down, side-to-side) those joints actually drive, and it names no tongue-specific blendshapes or GUI sliders in MetaHuman Creator. The capability appears real at the rig/skeleton level, but richer than a simple protrusion control is not explicitly confirmed in writing — only the joint hierarchy is.

### Cited Findings
- Epic's MetaHuman DNA documentation names four tongue joints — `FACIAL_C_Tongue1`, `FACIAL_C_Tongue2`, `FACIAL_C_Tongue3`, `FACIAL_C_Tongue4` — listed under "volume joints that will NOT be positioned automatically during bind pose updates," meaning they must be positioned manually if adjusted — [MetaHuman DNA (Rig Definition and Rig Operation)](https://dev.epicgames.com/documentation/metahuman/metahuman-dna-rig-definition-and-rig-operation?lang=en-US)
- The same page does not mention tongue blendshapes, tongue-specific Rig Logic channels, or tongue controls in the facial GUI — the word "tongue" appears only in the joint lists — [MetaHuman DNA (Rig Definition and Rig Operation)](https://dev.epicgames.com/documentation/metahuman/metahuman-dna-rig-definition-and-rig-operation?lang=en-US)
- Epic's free DNACalib/DNAViewer toolset (MetaHuman DNA Calibration Library) can edit, remove, or inspect joints and blendshapes in a DNA file, which is how a deeper joint-by-joint inspection of tongue articulation ranges could be done if needed — [MetaHuman DNA Calibration GitHub](https://redirect.github.com/EpicGames/MetaHuman-DNA-Calibration); [CG Channel coverage](https://www.cgchannel.com/2022/11/epic-games-releases-metahuman-dna-calibration-library/)
- An Unreal Fest 2024 talk titled "Anatomy of a MetaHuman Rig" claims to cover "LODs, meshes, blendshapes, skeletal structure, and facial animations," but the forum thread describing it does not state whether tongue joints are discussed in the talk itself — [Unreal Fest 2024 thread](https://forums.unrealengine.com/t/talks-and-demos-anatomy-of-a-metahuman-rig-unreal-fest-2024/2342837)

### Inferences
- The existence of four separate tongue joints (vs. a single bone) suggests the rig is built to support more than binary protrusion — likely tip curl/roll articulation similar to a game-character tongue rig — but this is an inference from joint count, not a confirmed capability described in Epic's prose documentation.
- Because these joints are explicitly excluded from automatic bind-pose positioning, any production use (e.g., driving them from audio) would likely require custom rig logic or manual animation setup rather than an out-of-the-box "tongue expression" slider in MetaHuman Creator.

### Gaps
- No Epic documentation was found that explicitly states the range of motion (curl, roll, lateral movement) the four tongue joints support, or confirms/denies dedicated tongue blendshapes exist in the DNA's expression set.
- Could not confirm whether MetaHuman Creator's web-based face GUI exposes any user-facing tongue control at all (vs. the joints only being accessible via Control Rig/Sequencer/DNA-level animation).

## Does NVIDIA's full Omniverse Audio2Face desktop application support driving MetaHuman's tongue specifically from audio, and is this workflow documented/used in practice?

### Takeaway
The Audio2Face desktop app did add tongue blendshape support (per its 2023.1 release notes) and NVIDIA's own ACE Unreal plugin docs confirm Audio2Face output is used with MetaHuman characters in Unreal — but real-world reports describe tongue mapping as fragile (sometimes only the tongue tip animates), and critically, the standalone Audio2Face desktop app itself was deprecated by NVIDIA as of October 2025, alongside the Omniverse Launcher used to install it.

### Cited Findings
- A web search summary of NVIDIA's Audio2Face 2023.1 release notes states the release added "LiveLink and Avatar Streaming," enabling streaming of blendshape animation from Audio2Face to Unreal Engine, "along with improved BlendShapes with added Tongue support" — [Audio2Face 2023.1 Release Highlights](https://docs-prod.omniverse.nvidia.com/audio2face/latest/release-notes/2023_1_highlights.html) (note: direct fetch of this page returned HTTP 404 during this research session; this finding is from the search engine's cached summary of the page, not a verified direct read — treat as moderately, not fully, confirmed)
- NVIDIA's ACE Unreal plugin documentation states Audio2Face features "work well with MetaHuman characters in Unreal Engine," but warns that MetaHuman's default `MouthClose` animation can interfere with Audio2Face lip movement and must be bypassed — [Character Animation docs, NVIDIA ACE Unreal Plugin](https://docs.nvidia.com/ace/ace-unreal-plugin/2.3/ace-unreal-plugin-animation.html)
- On an NVIDIA developer forum thread about transferring eye/tongue/jaw animation to a blendshape model, staff member Ehsan.HM describes the tongue as "the most complex" of the animatable parts because "both transform and vertices are animated," and recommends generating custom tongue blendshapes (e.g., `TongueUp`, `TongueDown`, `TongueCurlUp`, `TongueStretchOut`) solved via Audio2Face's BlendShapeSolve/Data Conversion tooling — [Transferring eye, tongue and jaw animations to blendshape model](https://forums.developer.nvidia.com/t/transferring-eye-tongue-and-jaw-animations-to-blendshape-model/261269)
- In the same thread, a user (stu9354) reports that in their actual result, "only the tongue tip moved" in the output mesh even though other parts of the tongue moved in the driver/reference mesh, and NVIDIA's own staff responder said he was "not quite sure why" and offered no fix — [same thread](https://forums.developer.nvidia.com/t/transferring-eye-tongue-and-jaw-animations-to-blendshape-model/261269)
- A user in the same thread suspected custom tongue deformations might not match what the Audio2Face solver expects "except for tip up and down," implying standard MetaHuman-style face rigs have "no tongue equivalent" that cleanly matches Audio2Face's internal tongue model — [same thread](https://forums.developer.nvidia.com/t/transferring-eye-tongue-and-jaw-animations-to-blendshape-model/261269)
- NVIDIA's own legacy-tools page confirms the Omniverse Launcher — the mechanism used to install the standalone Audio2Face desktop app — was deprecated effective October 1, 2025, and the Exchange "will no longer be accessible for installing applications" — [NVIDIA Omniverse Launcher (Deprecated)](https://developer.nvidia.com/omniverse/legacy-tools)
- An NVIDIA forum moderator explicitly stated: "A2F the app, has been depreciated. Along with Launcher. A2F, the NIM and plugin, is still alive, but we do not support it here on this Forum" and separately "The app itself, Audio2Face is gone. It is depreciated." — [MetaHuman Lip-Sync After Omniverse Launcher Support Ends](https://forums.developer.nvidia.com/t/metahuman-lip-sync-after-omniverse-launcher-support-ends/328855)

### Inferences
- The combination of (a) a known, NVIDIA-acknowledged bug/limitation where tongue retargeting to a custom rig may only drive the tip, and (b) the desktop app's deprecation, means this is not currently a dependable, actively-supported path for driving a MetaHuman's (or any custom rig's) tongue from audio — even setting aside the question of getting that data into Babylon.js at all.
- Going forward, NVIDIA's supported audio-driven facial path is the Audio2Face-3D SDK/NIM microservice line (already covered by other research in this project), not the deprecated desktop GUI app — so any future tongue-from-audio pipeline using NVIDIA tech would need to target that microservice architecture, not the Omniverse desktop app this question asked about.

### Gaps
- Could not directly verify the exact wording of the Audio2Face 2023.1 release notes (page returned 404 on direct fetch); the "added Tongue support" claim rests on a search-engine-cached summary of that page, not a primary-source read in this session.
- No documentation or forum report was found describing a complete, currently-working, step-by-step "audio to MetaHuman tongue" pipeline in production use — all tongue-specific evidence found describes partial success or unresolved bugs.

## Can MetaHuman assets or retargeted facial animation data be exported to glTF/VRM or any format Babylon.js can load, preserving tongue animation?

### Takeaway
Yes, MetaHuman data can technically leave Unreal in several forms (DNA files, FBX, and a community glTF exporter), but none of the paths found preserve real tongue articulation: the glTF export route only carries the standard ARKit blendshape set, which has a single, crude `tongueOut` shape — nowhere close to the four-joint tongue rig found in question 1 — and the DNA format itself is Epic-proprietary and version-locked, built for round-tripping within the Unreal/Maya/Houdini ecosystem, not for driving a tongue rig in Babylon.js.

### Cited Findings
- Epic's official MetaHuman Creator export tool supports DCC Export (Maya/Houdini), Geometry Export, DNA Export, and Materials Export — it does not offer a glTF export option — [MetaHuman Creator export tool in Unreal Engine](https://dev.epicgames.com/documentation/metahuman/metahuman-creator-export-tool-in-unreal-engine?lang=en-US)
- A free, third-party Unreal plugin, "Export Metahuman as glTF + ARKit" (Fab marketplace), exports only the MetaHuman **head mesh** as glTF with ARKit blendshapes derived from Unreal's Control Rig mappings; its listing does not mention tongue geometry, tongue blendshapes, or tongue animation at all, and it explicitly notes its `MouthClose` shape is only "an approximation" — [Fab listing: Export Metahuman as glTF + ARKit](https://www.fab.com/listings/88fa82af-3210-42e1-81f0-9a613da436ef)
- The standard Apple ARKit 52-blendshape set (the target format for that exporter) contains exactly one tongue-related shape, `tongueOut`, a single 0–1 float — there is no ARKit shape for curl, roll, or lateral tongue movement — [Unity Live Capture ARKitFaceCapture docs](https://docs.unity3d.com/ja/Packages/com.unity.live-capture@4.0/api/Unity.LiveCapture.ARKitFaceCapture.FaceBlendShapePose.html); corroborated by a community avatar blendshape reference describing the tongue group as "Tongue (1 morph target)" — [Avatar Blendshapes (Morph Targets)](https://boeni-industries.github.io/aico/subsystems/frontend/avatar-blendshapes)
- Epic explicitly calls MetaHuman DNA "our proprietary data format" that "encodes all information necessary to assemble and configure a full MetaHuman head, body and its rigs," and the format is versioned — Epic's own Expression Editor "is only compatible with DNA files created by MetaHuman Creator in Unreal Engine 5.6 or later" — [MetaHuman DNA documentation](https://dev.epicgames.com/documentation/metahuman/metahuman-dna-rig-definition-and-rig-operation?lang=en-US)
- DNA files can be exported (.dna) and edited outside Unreal via Epic's own Maya/Houdini tooling or community add-ons like Poly Hammer's Character DNA add-on for Blender (free base edition, supports DNA from UE 5.6+) — but this tooling is oriented toward re-importing edited DNA back into Unreal/MetaHuman-compatible pipelines, not toward producing a Babylon.js-ready glTF/VRM rig — [Working with DNA on a customized MetaHuman](https://dev.epicgames.com/documentation/metahuman/working-with-dna-on-a-customized-metahuman-in-unreal-engine); [Poly Hammer Character DNA add-on docs](https://docs.polyhammer.com/character-dna-addon/free-features/output/)
- A forum report notes that even Unreal's general-purpose glTF exporter plugin (unrelated to MetaHuman specifically) has historically been "in beta" and prone to crashes — [search summary of Unreal Engine forums, "Metahuman to gltf" thread](https://forums.unrealengine.com/t/metahuman-to-gltf/226635)

### Inferences
- No evidence was found of any pipeline — official or community — that exports a MetaHuman's tongue joints (or any tongue articulation richer than ARKit's single `tongueOut` shape) into glTF or VRM. The realistic ceiling for "tongue in Babylon.js sourced from MetaHuman" is a crude binary/scalar tongue-out shape, which is no better (likely worse, since it is 1 DOF) than what a custom Babylon/VRM blendshape rig could already define directly.
- Because DNA is proprietary, versioned, and coordinate-system-specific to Unreal, treating it as a general interchange format for a non-Unreal runtime is not realistic; it is designed for round-tripping between Unreal and specific DCC tools (Maya, Houdini, Blender via community add-ons), not for export to web/WebXR engines.

### Gaps
- No direct evidence (documentation, tutorial, or forum report) was found of anyone successfully retargeting MetaHuman's actual 4-joint tongue rig onto a non-MetaHuman skeleton, glTF, or VRM model. This should be treated as very likely infeasible rather than merely undocumented, given the proprietary/versioned nature of DNA and the narrowness of the one community glTF exporter found.
- Could not confirm current pricing/licensing restrictions on the Fab glTF+ARKit plugin itself beyond it being listed free ($0.00); its listing's license-terms field showed only a dash.

## If MetaHuman data cannot reasonably leave Unreal, what would actually be required to use MetaHuman for this project — would it mean rebuilding in Unreal instead of Babylon.js/WebXR?

### Takeaway
Yes — adopting MetaHuman for real tongue articulation would effectively mean abandoning the current client-rendered, static-hosted (GitHub Pages) Babylon.js/WebXR deployment model. Unreal Engine has no native WebXR or browser export; the only Epic-documented way to reach a browser at all is Pixel Streaming, which is a fundamentally different architecture (server-side GPU rendering streamed over WebRTC, not a client-side WebGL/WebXR app), and Epic's own docs mark VR streaming through this path as experimental.

### Cited Findings
- Epic Games does not ship a native browser or WebXR export target for Unreal Engine; as of UE 4.24, Epic moved HTML5 support out of the engine entirely to a community-maintained Platform Extension, and UE5 has no first-party HTML5/WebGL export — [summary of community reporting, "Unreal Engine HTML5 export, what happened and what works now"](https://www.summerengine.com/de/make-great-games/unreal-engine-html5-export.md); corroborated by an itch.io developer stating "Unreal Engine 5.6 does not officially support WebGL or browser-based deployment" (via search summary)
- Epic's own documentation describes Pixel Streaming as using "the WebRTC peer-to-peer communication framework for the lowest possible latency" to deliver "fully-rendered Unreal Engine experiences" to a browser — i.e., the Unreal application runs on a server/workstation and streams video+input to the browser client, rather than the browser running the 3D content itself — [Overview of Pixel Streaming in Unreal Engine](https://dev.epicgames.com/documentation/unreal-engine/overview-of-pixel-streaming-in-unreal-engine)
- A forum user notes that streaming a VR/Pixel Streaming experience is "currently in an experimental stage," per Epic's own 5.2/5.3 experimental-features documentation referenced in that thread — [search summary citing forum discussion](https://forums.unrealengine.com/t/vr-pixel-streaming-on-ue5-3-1-right-eye-only-1-3-visible/1549347)
- Independent forum bug reports describe broken stereo rendering when attempting Pixel Streaming to a VR/WebXR browser client: one report of "right eye only 1/3 visible" with "resolution is really bad" on UE 5.3.1 via Meta Quest Browser's Immersive WebVR View, and a separate report of "one eye black" — [VR Pixel Streaming on UE5.3.1 Right Eye Only 1/3 Visible](https://forums.unrealengine.com/t/vr-pixel-streaming-on-ue5-3-1-right-eye-only-1-3-visible/1549347); [Pixel Streaming in VR: one Eye black](https://forums.unrealengine.com/t/pixel-streaming-in-vr-one-eye-black/1228075)
- A forum comment flags a directional mismatch relevant to this project's needs: "WebXR is for streaming FROM web TO vr, not the other way around," relevant if the goal is to get Unreal content displayed via WebXR rather than consuming web content inside Unreal (via search summary of forum discussion)
- A commercial hosting vendor (Eagle 3D Streaming) markets VR Pixel Streaming claimed to reach "Oculus Quest 2, Quest 3, and other WebXR-compatible headsets," but recommends UE 5.5 specifically and disabling OpenXR to avoid its own WebXR rendering path conflicting with it — this is vendor marketing material, not independently verified or from Epic — [Eagle 3D Streaming VR Pixel Streaming](https://eagle3dstreaming.com/features/enhancements/vr-pixel-streaming)

### Inferences
- Even in the best case (a working, non-experimental Pixel Streaming setup), this is not a drop-in replacement for the current architecture: it requires a continuously running GPU-backed server/cloud instance to render Unreal and stream it, rather than a static site (GitHub Pages) serving a client-side WebGL/WebXR scene. That is a material shift in hosting cost, infrastructure complexity, and latency characteristics (network-dependent, not local-GPU-dependent) — not just a rendering-engine swap.
- Given the experimental status and reported stereo-rendering bugs specifically in VR/WebXR streaming contexts, Pixel Streaming for an actual immersive, head-tracked WebXR session (not just a flat video stream) should be treated as unreliable/unproven today, separate from its more mature use for non-VR "streamed app in a browser tab" scenarios.
- The practical conclusion: using MetaHuman for this project would most realistically mean rebuilding the experience as a native Unreal Engine VR application (PC VR or Quest-native via Unreal's standard OpenXR-based VR deployment), deployed through app installation rather than a browser link — not a continuation of the "visit a URL, enter WebXR" GitHub Pages workflow this project currently uses.

### Gaps
- No official Epic documentation was found that specifically addresses WebXR (as opposed to generic browser/Pixel Streaming) support; all WebXR-specific claims found are either community/vendor claims or bug reports, not Epic's own stated position.
- Could not verify whether Pixel Streaming's experimental VR limitations have been resolved in the most recent Unreal Engine version as of this research (version-specific status beyond the 5.2/5.3-era reports was not confirmed).

## Is MetaHuman actually free to use for a university VIP research project (non-commercial)?

### Takeaway
Financially, yes in practice — since UE5.6, MetaHuman use is governed by the standard Unreal Engine EULA, which is free for any user/organization under $1M USD in annual gross revenue (a university research project would clearly qualify), with no payment due regardless of commercial vs. non-commercial status at that scale. However, there is no dedicated "academic" or "non-commercial research" license, and Epic has explicitly told a forum requester there are no plans to create one — users are pointed to the general MetaHuman EULA, which has historically contained AI/deep-learning-use restrictions worth checking given this project uses audio-to-expression ML models.

### Cited Findings
- MetaHuman's own licensing page (per search-engine summary) states MetaHuman is "included as part of your standard Unreal Engine license," making it "free to use for anyone making under $1 million USD in revenue," with standard Unreal Engine terms applying above that threshold; since UE5.6, MetaHuman falls under the general Unreal Engine EULA rather than a separate MetaHuman Creator EULA (direct fetch of metahuman.com/license redirected to an Epic login wall and could not be read directly in this session — treat this specific summary as moderately, not fully, confirmed)
- A secondary industry write-up (CG Channel, June 2025) reports the same structure: "MetaHuman is included as part of your standard Unreal Engine license," free under $1M revenue, standard terms above it, and that as of that update MetaHuman characters/animations are classified as "non-engine products," usable in other engines (e.g., Unity, Godot) without Epic's usual 5% revenue-share cut on Unreal-made games — [CG Channel: "You can now sell MetaHumans, or use them in Unity or Godot"](https://www.cgchannel.com/2025/06/you-can-now-sell-metahumans-or-use-them-in-unity-or-godot/) (via search summary); a secondary tech-press summary of the same story adds that larger studios above the threshold pay "an $1,850 per-seat annual licence," and that "feeding MetaHumans back into training data is off-limits" — [Digital Production: "MetaHumans Graduate..."](https://digitalproduction.com/2025/06/05/metahumans-graduate-ready-for-unity-godot-and-the-fab-cash-register/)
- On an Unreal Engine forum thread asking about an academic license for MetaHumans, Epic community manager Nina Ward directly replied (April 2021): "We do not have plans to offer this," and referred the poster to "the MetaHuman EULA, section 1.2" for details — no further detail on that section's content was available in the thread itself — [Academic license thread](https://forums.unrealengine.com/t/academic-license/226746)
- A separate forum discussion (referenced via search summary, not independently confirmed) describes an older MetaHuman FAQ as having stated MetaHumans "can't be used for any deep learning or similar technology," with a later report claiming Epic's revised license "now allows AI training on Unreal Engine source code, content they create and MetaHuman outputs" — this later claim comes from a secondary tech-news aggregator (Digg) summarizing an Epic license update, not from Epic's text directly — [Digg: "Epic updates Unreal Engine license to allow AI training..."](https://digg.com/ai/5ngjinvr) (via search summary)
- Direct attempts to fetch Epic's primary EULA pages in this session failed: `metahuman.com/license` redirected to an Epic account login wall, and `unrealengine.com/en-US/eula/mhc` returned HTTP 403 Forbidden — neither could be read directly, so all licensing specifics above rely on secondary summaries/search-engine caches rather than a verified primary-source read

### Inferences
- For a university VIP research project with no product revenue, the $1M threshold is a non-issue — cost is not the practical barrier to using MetaHuman.
- The more relevant risk for this specific project is the "no training data / AI use" restriction Epic has historically applied to MetaHuman content, given that the project's stated workflow involves feeding animation through audio-to-expression ML models (Audio2Face / LAM Audio2Expression, per other work already in this repo). Whether the current EULA still restricts this, and whether using a MetaHuman as a visual asset driven by an external ML model (rather than training a model on MetaHuman data) would even trigger that clause, is unresolved from secondary sources alone and should be confirmed by reading Epic's current EULA text directly (not through this session's blocked fetches) before proceeding.

### Gaps
- Could not directly read Epic's current, authoritative MetaHuman/Unreal Engine EULA text in this session (both primary URLs attempted were blocked — one by a login redirect, one by a 403). All licensing conclusions above are from secondary summaries and should be verified against Epic's actual EULA before any commitment is made.
- Could not confirm the exact current text of "MetaHuman EULA section 1.2" referenced by Epic staff in 2021, nor whether that section's restrictions (or the AI-training clause reportedly relaxed in 2025) still apply, have changed, or apply differently to non-commercial academic research specifically.
