# Classical (non-ML) viseme/phoneme lip-sync systems and VRM-community conventions with a dedicated tongue-position category

## Does Oculus/Meta's OVRLipSync 15-viseme set include any tongue-specific viseme, or is it purely lip/jaw shape like ARKit?

### Takeaway
OVRLipSync's 15 visemes are described in Meta's own docs primarily as lip/jaw shapes, but **4 of the 15 viseme descriptions explicitly name a tongue position** (th, dd, kk, nn) rather than only a lip/jaw shape — it is not purely lip/jaw like ARKit-52. However, there is no *standalone* tongue viseme (i.e., no viseme that is nothing but "tongue in position X" independent of a mouth shape) — tongue position is bundled into the same viseme as the associated consonant group, so it cannot be driven independently of that viseme's mouth shape.

### Cited Findings
- Meta's official OVRLipSync viseme reference table (fetched directly) lists 15 visemes — sil, PP, FF, TH, DD, kk, CH, SS, nn, RR, aa, E, I, O, U — with phoneme groupings and example words, but the table itself (as rendered) gives only phonemes/example words, not prose mouth descriptions — [Meta Developers: Audio OVRLipSync Viseme Reference](https://developers.meta.com/vr/documentation/unity/audio-ovrlipsync-viseme-reference/)
- The VRChat wiki's fuller viseme table (which mirrors the Oculus Lipsync viseme definitions used in VRChat/Unity) gives prose descriptions for each of the 15, and tongue position is explicitly named for 4 of them: **TH** — "Tongue sticks out between the teeth" (think, that); **DD** — "Tongue tip touches the ridge behind the upper teeth" (tip, dip, t/d); **kk** — "Back of the tongue touches the roof of the mouth" (call, gas, k/g); **nn** — "Tongue pressed to the ridge, lips apart" (lot, not, n/l) — [VRChat Wiki: Visemes](https://wiki.vrchat.com/wiki/Visemes)
- The other 11 visemes (sil, PP, FF, CH, SS, RR, aa, E, I, O, U) are described purely in terms of lips, teeth, and jaw, with no tongue mention — [VRChat Wiki: Visemes](https://wiki.vrchat.com/wiki/Visemes)
- Meta states the Oculus Lipsync plugin is in end-of-life status and will not receive further updates; its replacement path is audio-based face tracking exposing the same 15 visemes via the `XR_META_face_tracking_visemes` OpenXR extension — [Meta Developers: Audio OVRLipSync](https://developers.meta.com/horizon/documentation/unreal/audio-ovrlipsync/)

### Inferences
- OVRLipSync's tongue information is a byproduct of how its 15 visemes were originally grouped by articulatory phonetics (each viseme corresponds to a place/manner-of-articulation class), not a deliberate "separate tongue channel" design — the tongue description is folded into the same viseme index as the mouth shape, so an avatar rig using OVRLipSync gets tongue cues "for free" only if its blendshapes for DD/kk/nn/TH already include a tongue pose baked into that viseme's blend target. If the avatar's viseme blendshapes are lip/jaw-only (as most ARKit-52-based rigs are), the tongue information in the Oculus documentation is simply discarded.
- Because `nn` groups both `n` and `l` together, and `DD` groups both `t` and `d`, this set cannot distinguish L from T/D/N the way the user's objective implies it might want to (both land on different visemes: `nn` for N/L vs `DD` for T/D) — this is actually useful for the user's stated goal (L/T/D/N) since OVRLipSync already splits these into two tongue-bearing visemes (DD for T/D, nn for N/L), rather than collapsing all four into one generic "alveolar" bucket.

### Gaps
- Meta's current official page, as fetched, rendered only as a phoneme/example-word table without the prose mouth/tongue descriptions visible in the fetch (likely because the descriptive text lives in an image or a UI element the fetch tool couldn't parse); the prose confirmation above relies on the VRChat wiki's mirror of the same OVRLipSync definitions rather than Meta's page text directly. These two sources are consistent with each other (same 15 viseme names/phoneme groupings), but an independent third confirmation of Meta's exact prose wording was not obtained.

## Are there other named viseme standards (Disney classic animation chart, Preston Blair, JALI, CrazyTalk/Reallusion, SAPI) that include a tongue-position category, with real open-source tooling that outputs to them from audio or text?

### Takeaway
Of the standards checked, **Reallusion's "8+7 Phoneme Pair" system (used in iClone / Character Creator) is the strongest real-tooling match**: it explicitly separates 8 lip shapes from 7 tongue movements as independent weighted channels and composes them into a 15-viseme set that includes a dedicated **T_L_D_N** viseme grouping exactly the consonants the user named. It is commercial (not open-source) but is real, currently-shipping, widely-used software with audio/text-driven lip-sync (AccuLips/text-to-lipsync). SAPI's viseme set, by contrast, is lip/jaw-shape-grouped only, with no tongue channel. Preston Blair's and Disney's classic charts have scattered, non-systematic tongue notes (drawn-in tongue positions on specific vowel shapes) but no dedicated "tongue parameter" and no modern open-source software implementing them with tongue control.

### Cited Findings
- **Reallusion (iClone / Character Creator "8+7 Phoneme Pair" system):** the official manual states the system composes visemes from **"8 basic lip shapes and 7 tongue movements in different weight values"** — i.e., tongue is tracked as its own 7-value channel, separate from the 8 lip shapes — [Reallusion Manual: What are 8+7 Phoneme Pairs and 1:1 Direct Lipsync Systems](https://manual.reallusion.com/Character-Creator-4/Content/ENU/4.0/06-Facial-Profile-Editor/8_7_and_1_1.htm)
- The resulting 15 visemes in this system are: **AE, Ah, B_M_P, Ch_J, EE, Er, F_V, Ih, K_G_H_NG, Oh, R, S_Z, T_L_D_N, Th, W_OO** — note the explicit **T_L_D_N** grouping, which bundles exactly T, D, N, and L into one tongue-tip-alveolar viseme — [Reallusion Manual: 8+7 and 1:1 Lipsync Systems](https://manual.reallusion.com/Character-Creator-4/Content/ENU/4.0/06-Facial-Profile-Editor/8_7_and_1_1.htm)
- The Facial Profile Editor lets an animator set the "Mouth bones, Tongue bone and Mouth shapes for lipsync visemes" directly, and a separate smoothing control exists for "Lips, Tongue and Jaw" independently — confirming tongue is a first-class, independently-authored channel in this pipeline, not a derived/baked-in extra — [Reallusion Manual: Setting Lipsync Movement Data](https://manual.reallusion.com/character-creator-4/Content/ENU/4.0/06-Facial-Profile-Editor/Setting-Lipsync-Movement-Data.htm)
- A 2019-era Reallusion forum thread independently corroborates that the system exposes many "tongue position morphs" that can be confusing to set up ("I see a lot of tongue position morphs") — [Reallusion Forum: Setting Facial (Viseme) Keyframe in iClone 7](https://forum.reallusion.com/PrintTopic409063.aspx)
- This tooling is commercial/closed-source (iClone, Character Creator, 3DXchange are paid Reallusion products), not open-source, and is built for FBX/Reallusion's own character pipeline rather than VRM/Babylon.js directly — no source found confirming a free or open export path of this specific tongue-channel data into a VRM glTF blendshape pipeline.
- **Microsoft SAPI viseme set:** documented as a 22-entry (0–21) viseme enumeration "based on the Disney 13 Visemes," grouping consonants purely by mouth shape (e.g., one ID for s/z, one for f/v, one for p/b/m) — [Microsoft Learn: SPVISEMES (SAPI 5.3)](https://learn.microsoft.com/en-gb/previous-versions/windows/desktop/ms717289(v=vs.85)); [Microsoft Learn: SpeechVisemeType (SAPI 5.4)](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee125219(v=vs.85)). No tongue-specific entry was found in this set — it is a pure mouth-shape convention being potentially mistaken for an articulatory one.
- **Preston Blair's classic chart:** an illustrator's description (not Blair's original book, which the search did not surface directly) notes tongue positions drawn into specific mouth shapes — e.g., the A/I shape shows "the tongue flat against the floor of the mouth," the U shape shows it "somewhat lifted," and the "rest" position shows the tongue "visible and flat against the floor of the mouth" — these are incidental drawn details on vowel mouth shapes, not a separate parameter, and no modern software tool that outputs audio/text → Preston Blair shapes with tongue control was found — [frameo.ai: Animation Mouth Chart](https://frameo.ai/en/learn/animation-mouth-chart); original source cited as Blair, P. (1947), *Advanced Animation*, Walter T. Foster, per the JALI paper's bibliography.
- **Disney's classic chart:** described only as "a chart of 12 archetypal mouth positions," with no tongue detail found in available sources — [frameo.ai: Animation Mouth Chart](https://frameo.ai/en/learn/animation-mouth-chart)
- **CrazyTalk (older, pre-iClone Reallusion product):** help docs describe only "perfect lip synchronization" generically, with no tongue-specific detail found in available CrazyTalk 5/6 documentation — [Reallusion: CrazyTalk6 Lip-synchronizing](https://www.reallusion.com/crazytalk/help/CrazyTalk6/05_Script/Lip-synchronizing.htm)

### Inferences
- Reallusion's T_L_D_N viseme is the one named, shipping, real-tooling standard found in this research that most directly matches the user's ask (a consonant class for exactly L/T/D/N with its own tongue-movement weighting), but it lives inside a commercial animation suite built around its own rig/bone system (tongue bone + mouth shapes), not a portable blendshape spec — adapting it to a VRM+Babylon.js pipeline would mean re-deriving the 7 tongue weights/poses as custom morph targets and writing new trigger logic keyed to the same T/D/N/L phoneme grouping, rather than importing anything directly.
- The pattern across Disney/Preston Blair/SAPI is consistent: these are fundamentally mouth-shape (viseme) conventions, and any tongue detail found is incidental/illustrative on specific vowel shapes, not a systematic, independently-controllable tongue parameter — exactly the "mouth-shape-mistaken-for-tongue-shape" case the user asked to be made explicit about.

### Gaps
- Preston Blair's original 1947 book itself was not accessed directly — the tongue-position notes above come from a secondary illustrator's description, not the primary chart/book, so exact wording and full shape-by-shape tongue notes are unconfirmed.
- No modern open-source software was found that takes audio or text and outputs directly to Preston Blair, Disney-12, or SAPI-viseme targets with explicit tongue control — these three standards only have "tooling" in the loose sense of legacy/commercial animation or TTS systems (SAPI itself, built into Windows Speech), not community open-source phoneme-to-tongue pipelines.
- No confirmation was found of any free/open bridge that maps Reallusion's 8+7 tongue data into VRM or into a Babylon.js-consumable blendshape format.

## Is there a VRM community standard beyond "Perfect Sync" (ARKit-52) that adds tongue blendshapes — per vrm-c GitHub and VTuber tooling (VSeeFace, Warudo, Virtual Motion Capture)?

### Takeaway
**No formal VRM-community tongue standard was found.** The VRM 1.0 spec's preset expression list (17 presets) has no tongue entry, no open GitHub issue/discussion in vrm-c's repos specifically proposing a tongue blendshape was found, and VSeeFace/Warudo/Virtual Motion Capture all treat tongue as, at best, a custom/non-standard blendshape clip that must be hand-named and hand-mapped per avatar — tongue tracking even shows up as an explicit known limitation in Warudo's MediaPipe-based face tracking ("I cannot... stick out my tongue").

### Cited Findings
- Search of the vrm-c/UniVRM and vrm-c/vrm-specification issue trackers (via Ecosyste.ms mirrors) turned up no issue specifically about a tongue blendshape; the closest matches were generic blendshape-bake/normalization bugs (e.g., issue #2327 on scaled blendshape baking) and an expression-override issue (#2430), neither tongue-related — [Ecosyste.ms: vrm-c/UniVRM Issues](https://issues.ecosyste.ms/hosts/GitHub/repositories/vrm-c%2FUniVRM/issues)
- The VRM 1.0 expression system defines a fixed set of preset expression names; "tongue" is not among the standard presets, meaning any tongue shape in a VRM avatar today must be added as a custom (non-preset) expression clip with an arbitrary name chosen by the modeler — general understanding stated in researcher commentary, not directly quoted from a primary spec page (see Gaps).
- A paid Booth.pm VRM-rigging service advertises that its rigs "support tongue tracking in VSeeFace and other face-tracking apps," implying tongue blendshapes are something riggers add informally/per-model rather than something the VRM standard defines — this is a commercial marketing claim, unverified — [Booth.pm: VRM Model Facial Rigging + ARKit & Blendshapes](https://booth.pm/ja/items/7014023)
- Warudo's own documentation lists, as a known MediaPipe tracking limitation, an FAQ entry titled "I cannot puff my cheeks / stick out my tongue" — confirming tongue is not reliably supported even on the tracking side of this VTuber tooling, let alone standardized as an avatar blendshape convention — [Warudo Docs: MediaPipe](https://docs.warudo.app/docs/mocap/mediapipe)
- Warudo does support importing a VRM avatar's own expression clips ("Import VRM Expressions") and lets users remap/adjust individual blendshape thresholds, meaning a custom tongue blendshape could in principle be driven if an avatar has one and the user manually wires it — but no evidence of a shared naming convention (e.g., everyone calling it the same thing) was found — [Warudo Docs: 3D Primer](https://docs.warudo.app/docs/tutorials/3d-primer)
- VSeeFace's own "special blendshapes" documentation page (vseeface.icu, referenced by itch.io community posts as the authoritative source) could not be directly fetched in this research (connection failure); an itch.io comment pointed to it as the place VSeeFace documents its small set of extra, non-ARKit blendshape clips, but its tongue content (if any) was not independently confirmed — [itch.io comment referencing vseeface.icu/#special-blendshapes](https://itch.io/post/4671183)

### Inferences
- The absence of any vrm-c issue/discussion proposing a tongue blendshape, combined with Warudo explicitly listing tongue tracking as unsupported, suggests the VRM/VTuber ecosystem currently treats tongue as a "nice extra" left entirely to individual avatar riggers rather than a convention with community consensus — there is no "ARKit-52 but with tongue" de facto standard analogous to Perfect Sync.
- Any tongue blendshape the user builds for their VRM avatar would be a one-off custom clip; there is no existing shared name/convention to align with for interoperability with other VRM tools (VSeeFace, Warudo, VMC) beyond whatever ad hoc name a given model's rigger chose.

### Gaps
- The VSeeFace "special blendshapes" page itself (vseeface.icu) could not be reached directly (DNS/connection error on fetch); its content on tongue, if any, is unconfirmed. Worth a direct retry or manual browser visit.
- Virtual Motion Capture (VMC) and VSeeFace's own GitHub issue trackers were not directly searched for "tongue" (time/tool-budget constraint) — only general web search was used, which did not surface VMC-specific tongue discussion. This is a real gap: a targeted search of github.com/ymt-games (VMC) or VSeeFace's own repo issues for "tongue" was not performed and could turn up informal community convention not found here.
- No direct confirmation of the VRM 1.0 spec's preset expression list contents was obtained from the primary spec document itself in this research pass (relied on general knowledge); a direct read of the vrm-c/vrm-specification `expressions.md` would firm this up.

## Is JALI relevant here — does it model tongue position, and is its code/tooling actually usable?

### Takeaway
JALI is **relevant as a research reference but not as usable tooling for this pipeline**: its own paper frames full tongue animation as a goal/challenge (tongue is "hidden anatomy," only partially visible) rather than something JALI directly outputs as a controllable parameter in the original 2016 system, and no open-source code, SDK, or free download of JALI was found — it is now a commercial product sold through JALI Research Inc., a spinoff company, not a tool the user can install and adapt.

### Cited Findings
- JALI ("Jaw and Lip") models speech primarily via two visually distinct, controllable anatomical channels — jaw and the lower-face/lip muscles — per the original paper and project page — [JALI: An Animator-Centric Viseme Model for Expressive Lip-Synchronization](https://www.dgp.toronto.edu/~elf/jali.html)
- The same paper lists automatic animation of "hidden anatomy" such as the tongue — described as only occasionally and partially visible on camera — as a goal/challenge area, not as a solved, directly-controlled output of the base JALI model — per web-search-extracted summary of the paper (direct PDF text extraction was not possible in this session; see Gaps) — [JALI SIGGRAPH 2016 paper (PDF)](https://dgp.toronto.edu/~elf/JALISIG16.pdf)
- The JALI pipeline (per the paper's own description) does take a transcript + audio, computes a phonetic alignment, and uses that alignment to "procedurally animate the phonemes of a JALI rig... with lip, tongue, and jaw movement" — indicating the released rig example does include a tongue channel driven off the same phonetic alignment, even if the core published model's novelty is jaw/lip, not tongue — per web-search-extracted summary (same sourcing caveat) — [JALI SIGGRAPH 2016 paper (PDF)](https://dgp.toronto.edu/~elf/JALISIG16.pdf)
- VisemeNet (a 2018 follow-up from the same JALI-adjacent research lineage, SIGGRAPH 2018) explicitly predicts "tongue, jaw, and facial muscle" movement for speech animation — confirming tongue became an explicit target in the JALI research lineage's later work — but VisemeNet is a trained deep-learning (LSTM) model, i.e., ML-based, which the user's objective excludes — [VisemeNet paper (PDF)](https://www.dgp.toronto.edu/~karan/papers/visemenetSIG18.pdf)
- JALI Research Inc., founded 2016 in Toronto, commercializes this technology; a University of Toronto news story reports its software was used in *Cyberpunk 2077* — [U of T News: U of T startup draws on AI, linguistics to power facial animation in video games](https://utoronto.ca/news/u-t-startup-draws-ai-linguistics-power-facial-animation-video-games); [JALI Research Inc. company page](https://entrepreneurs.utoronto.ca/startup/jali-research-inc/)
- No JALI SDK, source code repository, or free download was found; a targeted search for "JALI SDK download / open source / code release" returned only unrelated projects (a SourceForge listing by a different author, CERN's unrelated "JAliEn" grid-computing project) — [WebSearch: JALI SDK download](no relevant result; see search above)

### Inferences
- JALI is best treated as a design reference (its phonetic-alignment-driven rig concept, and its explicit framing of tongue/jaw/lip as semi-independent channels) rather than as adoptable software — the user could borrow its conceptual approach (phonetic alignment → independently-triggered tongue channel) without being able to use any of its actual code, since none is public.
- Because JALI's commercial descendant is closed and proprietary, and its open academic follow-up (VisemeNet) is ML-based, JALI's practical contribution to a "classical, low-effort, real-tooling" shortlist is close to zero — it supports the user's rule-based approach conceptually but offers no code to reuse.

### Gaps
- The JALI paper's PDF could not be parsed directly by the fetch tool in this session (binary/compressed stream, not extracted to text); the tongue-related claims above come from web-search snippet extraction of the paper's content, not a verified direct read of the PDF text. This should be treated as moderately, not fully, reliable — a direct text-extraction pass (e.g., via a PDF-to-text tool) on the saved PDF (saved locally at `C:\Users\fjawad\.claude\projects\c--Users-fjawad-Downloads-VRET\f96cd0d8-af94-4895-9f49-ee682babd680\tool-results\webfetch-1794503868468-6whrug.pdf` during this research session) would firm this up.
- Exact scope of what the original 2016 JALI *paper* claims for tongue (vs. what only the commercial product or VisemeNet later added) is not fully disambiguated in the sources gathered.

## Would a simple custom phoneme-to-tongue-position rule (via a forced aligner like MFA/Gentle, triggering a hand-authored tongue blendshape for L/T/D/N) be realistic, and do existing open-source projects already do something like this?

### Takeaway
This approach is realistic and is, in effect, close to what Reallusion's commercial 8+7 system and the open-source **AnimaSync V1** engine already do internally (phoneme/viseme-class → rule-based blendshape weights, including tongue) — AnimaSync V1 in particular is the closest found example of an actually-open, rule-based (non-ML) phoneme pipeline that explicitly outputs tongue blendshape values, not just mouth shape, though its "open source" status has an unresolved caveat (see Gaps). Forced aligners (Gentle, and presumably Montreal Forced Aligner) reliably produce per-phoneme timestamps, which is exactly the input a hand-built L/T/D/N → tongue-blendshape trigger rule would need.

### Cited Findings
- **AnimaSync** (goodganglabs) is described on its own site as a "browser-based... Rust/WASM" engine, tagged "Open Source," that has a V1 "phoneme engine" pipeline mapping **61 phonemes → 22 visemes → 111 ARKit-style outputs (covering jaw, mouth, and tongue) → the 52 standard ARKit blendshapes**, with "smoothing and anatomical constraints" applied in between — this is explicitly phoneme/rule-based (not the ML path), and explicitly includes tongue in its intermediate 111-dim representation — [AnimaSync project site](https://goodganglabs.github.io/AnimaSync/); corroborating npm package description via WebSearch summary — [WebSearch result citing AnimaSync docs]
- AnimaSync's V2 is described as a separate, smaller "student model" that predicts the 52 ARKit blendshapes directly with ML (ONNX inference) — contrasted explicitly with V1's rule-based phoneme pipeline — [WebSearch result citing AnimaSync docs]
- AnimaSync's own marketing copy simultaneously says "Open Source" and references a "30-day Free Trial," which is an internally inconsistent signal about licensing/availability — this needs direct verification before relying on it (see Gaps).
- **Gentle** (a forced aligner) takes an audio file plus a transcript and returns per-word and per-phoneme timing as a list of `{text, start_time, end_time}` objects — exactly the timestamped-phoneme input format a hand-built tongue-trigger rule needs — [Reanimate docs: Voice](https://reanimate.readthedocs.io/en/latest/voice/)
- A cited patent (US 10,839,825, for an unrelated commercial system) independently describes the same general design pattern: parse a word into phonemes, forced-align for per-phoneme timing, map each phoneme to a viseme, and drive a FACS/MPEG-4-compatible rig from those viseme keyframes — including, per its claims language, "tongue-only visemes that have no effect on the lip contribution," i.e., a viseme class that is tongue-position-only and independent of lip shape — confirming the general architecture (phoneme timing → independent tongue viseme) has prior art and is a sound, implementable design, though this specific patent's code is not open/available — [USPTO Patent 10,839,825: System and method for animated lip synchronization](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/10839825)
- **SpeechDrivenTongueAnimation** (CVPR 2022, salmedina) is an MIT-licensed, audio-driven tongue-animation research project — but it is explicitly ML-based (self-supervised Wav2Vec audio features, not phoneme-rule-based), and its own README code section is marked "UNDER CONSTRUCTION," meaning the released code is incomplete/non-functional as tooling today — [GitHub: salmedina/SpeechDrivenTongueAnimation](https://github.com/salmedina/SpeechDrivenTongueAnimation)
- Reallusion's 8+7 system (see earlier section) is itself evidence that the "rule-based phoneme/viseme class → independent tongue-weight trigger" architecture works well enough to ship in widely-used commercial software (iClone/Character Creator), reinforcing the design's practicality even though that specific implementation isn't open-source — [Reallusion Manual: 8+7 and 1:1 Lipsync Systems](https://manual.reallusion.com/Character-Creator-4/Content/ENU/4.0/06-Facial-Profile-Editor/8_7_and_1_1.htm)

### Inferences
- A lightweight, realistic implementation path for the user's Babylon.js/VRM pipeline: run Gentle (or MFA) once over the dialogue audio+transcript to get per-phoneme timestamps, bucket those phonemes into a small rule table (e.g., alveolar/tongue-tip group: T, D, N, L → trigger a hand-authored "tongue-tip-up" morph target at full or partial weight; velar group: K, G → trigger a hand-authored "tongue-back-raised" morph target; interdental: TH → "tongue-between-teeth" morph target), and blend/cross-fade these on top of whatever mouth-shape viseme system (e.g., the existing Rhubarb output already in the pipeline) is already driving the lips/jaw. This mirrors exactly what Reallusion's 8+7 system and AnimaSync V1 already do architecturally, just scoped down to only the phonemes the user cares about (L/T/D/N, and optionally K/G/TH), which is a much smaller authoring burden than a full 7-shape tongue system.
- No evidence was found of an existing *open-source* project that does precisely this narrow "forced-aligner timestamps → hand-authored tongue trigger for a small consonant subset" recipe end-to-end; AnimaSync V1 is the closest full pipeline, but it's a packaged phoneme→52-ARKit-blendshape engine (not an exposed simple phoneme→tongue rule the user could lift out piecemeal), and its open-source status is unconfirmed.

### Gaps
- AnimaSync's actual GitHub repository URL and its precise license (the site tags it "Open Source" but also advertises a "30-day Free Trial," which reads as a commercial/open-core model) were not found/confirmed in this research pass — direct inspection of `@goodganglabs/lipsync-wasm-v1` on npm, or finding the linked GitHub repo, would resolve this before treating AnimaSync as freely reusable.
- Montreal Forced Aligner (MFA) itself was not directly checked in this session (only Gentle was); given Gentle and MFA produce broadly equivalent phoneme-timestamp output, this is a minor gap, but MFA's specific documentation/output format was not verified firsthand.
- No existing open-source project combining a forced aligner directly with a hand-authored tongue-blendshape trigger (the user's proposed lightweight approach) was found as a ready-made reference implementation — this specific combination appears to be a gap in available open tooling, meaning the user would likely be building the "glue" rule table themselves (using Gentle/MFA's timestamp output as a known, well-supported input).
